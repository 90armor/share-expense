# Decisions Log

- Prisma: npm's `latest` dist-tag for the `prisma` CLI package currently points to an unstable 8.0.0-rc build, while `@prisma/client`'s `latest` is stable 7.10.1. Pinned all Prisma packages to the exact stable version 7.10.1 to avoid an RC and a CLI/client mismatch.
- Prisma 7 requires a driver adapter for SQLite (no more bundled engine) — added @prisma/adapter-better-sqlite3 + better-sqlite3 + @types/better-sqlite3, approved by user as an exception to "no unapproved dependency."
- Config file is named prisma7.config.ts, not prisma.config.ts — this is what `prisma init` itself generates on Prisma 7.10+ for a fresh project, to avoid clashing with Prisma 8's config format.
- `prisma init` also offered to download third-party "agent skills" docs from GitHub into `.agents/`, `.claude/skills/`, `.windsurf/skills/`, and `skills-lock.json`. Re-ran with `--no-skills` to stay within "init only" scope.
- No PrismaClient wrapper file yet — deferred to the first feature PR that needs one (no models exist yet).
- Chose SQLite for local dev simplicity (file-based, no external DB server).
- Chose feature-folder structure under src/features (src/features/<name>), created per-feature as code lands rather than pre-scaffolded.
- Kept ESLint and Prettier as separate scripts (lint vs format) instead of eslint-plugin-prettier, to minimize dependencies.
- Added root .npmrc (save-exact=true) so every dependency this project installs from now on is pinned exactly.
- @types/node bumped from create-next-app's default `^20` to exact `24.19.2` (originally picked at `26.6.6`, re-pinned to `24.19.2` in the Docker PR once Node 24 was chosen as the project's pinned runtime) — local Node is currently v24.16.0, and `24.19.2` satisfies vitest 5.1.0's peer requirement (`^22.0.0 || >=24.0.0`).
- Kept the AGENTS.md create-next-app generates (Next.js-managed, regenerated by `next dev`); CLAUDE.md imports it via `@AGENTS.md` instead of duplicating its content, so project-specific rules stay only in CLAUDE.md.
- .prettierignore excludes README.md, docs/prompts/, AGENTS.md, and package-lock.json — pre-existing or generated content this PR doesn't own.
- `npm run typecheck` runs `next typegen` first — App Router's generated route types (`.next/types`) are gitignored build output, so a fresh clone has no route types until something generates them; folding `next typegen` into the script keeps `typecheck` self-sufficient without requiring a prior `dev`/`build` run.
- `next.config.ts`'s `cacheComponents`/`partialPrefetching`/`@tailwindcss/turbopack` rules are Next.js 16.4.6's `create-next-app` default output, left unedited. Since Cache Components is on, dynamic data (DB reads) must follow Suspense/`use cache` rules — check this first in the Phase 2 golden example.
- Added Docker support (Dockerfile + docker-compose.yml) for a reproducible dev environment — scoped to dev-container usage only; production deploy config is out of scope.
- Chose Node 24 as the pinned runtime (`.nvmrc`, `engines`, Docker base image, `@types/node`) — Node 24 LTS, supported until April 2028, matches local dev machine's v24.16.0.
- Added `output: "standalone"` to `next.config.ts` to support the Docker production `runner` stage (pruned standalone server output).
- Docker base image is `node:24-slim`, not `node:24-alpine` — `better-sqlite3` is a native addon; Alpine's musl libc causes native-module build/runtime issues that slim's glibc avoids.
- No Prisma models/migrations exist yet, so no `migrate deploy` entrypoint was added — deferred to the first feature PR that adds a model; it'll decide entrypoint script vs. separate `docker compose run` command.
- Build stage sets a dummy `DATABASE_URL=file:/tmp/build.db` before `prisma generate` — generate only reads the schema and never connects, but `prisma7.config.ts` requires the env var to be set or it errors.
- `.env` is not read by Claude and is not passed via `env_file` in compose, but the `.:/app` dev bind mount does make it visible inside the container, and `next dev` may load it itself; compose's `environment:` still wins for `DATABASE_URL`. Not claiming `.env` is invisible to the container — only that it's never read by tooling here or wired through compose config.
- The production-target verification (`docker build --target runner`) doesn't exercise the database — no application code imports `better-sqlite3`/Prisma client yet. The first feature PR that adds a model must re-verify the `runner` stage against real DB usage, and may need `serverExternalPackages` in `next.config.ts` for `better-sqlite3` to trace correctly into the standalone output.
- CI runs `npm ci` → `prisma generate` → `format:check` → `lint` → `typecheck` → `test` → `build`, in that order so cheap/fast checks (formatting, linting) fail before slower ones (typecheck, test, build).
- Pinned `actions/checkout` and `actions/setup-node` by major tag (`@v7`, both confirmed current via GitHub's release API) rather than full commit SHA — simpler to read/maintain, accepting that patch/minor updates apply automatically.
- CI sets a dummy `DATABASE_URL=file:/tmp/ci.db` at job level so `prisma generate` (schema-only, never connects) doesn't fail on a missing env var — same reasoning as the Docker build stage.
- Branch protection (require PR before merge, require the "CI" status check, no direct pushes to main) is configured manually in GitHub repo settings — not part of this PR.
