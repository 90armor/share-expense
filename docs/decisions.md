- `.claude/settings.json`'s env-file deny rules went from `Read(./.env)` + `Read(./.env.*)` + `Read(!.env.example)` to six explicit rules: `Read(./.env)`, `Read(./.env.local)`, `Read(./.env.development)`, `Read(./.env.production)`, `Read(./.env.test)`, `Read(./.env.*.local)`. The `!.env.example` negation carve-out was re-verified to work as intended — confirmed both by the official docs ("A deny or ask pattern that starts with `!` is a gitignore negation. It carves the paths it matches out of the `path` or `./path` rules listed before it," code.claude.com/docs/en/permissions) and by a live test (`.env.local`/`.env.production` denied, `.env.example` readable). It was replaced anyway, not because it was broken, but because the docs also state "A `!` rule listed first carves nothing out" — the carve-out only works if it stays ordered after the rules it exempts from, so a future reorder or a new deny entry added after it would silently re-block `.env.example` with no error. The explicit list has no such order-dependency; the tradeoff is that any new `.env.<name>` file needs its own line (`.env.*.local` is included to still auto-cover Next.js-style local override files like `.env.development.local`).
- `Read()` deny rules block Claude's built-in file tools and recognized Bash file commands (`cat`, `head`, `tail`, `sed`, `tee`, and redirections like `> file`/`< file`) from touching `.env`, but do not block `grep -r` (which doesn't name the file), custom scripts/subprocesses that open files themselves, or unrecognized commands — full enforcement against those is planned via PreToolUse hooks in Phase 6.
- Money is stored and computed as integer minor units (1/100) in a `bigint`, typed `Money = Readonly<{ amount: bigint; currency: CurrencyCode }>` (`src/lib/money.ts`). Not float: binary floating point cannot represent 0.10 exactly and drifts on sums. Not Prisma `Int`: it is 32-bit (max 2,147,483,647 minor units ≈ 21.4M MMK), too small for MMK/KHR group totals — the DB column will be Prisma `BigInt` (int64). Not Prisma `Decimal`: SQLite has no true decimal type. Across JSON/forms, amounts travel as strings (bigint is not JSON-serializable).
- Supported currencies are MMK, USD and KHR, all with 2 decimal places. One currency per group; no FX conversion. Arithmetic helpers (`addMoney`, `subtractMoney`, `sumMoney`) throw on a currency mismatch rather than returning a Result — under one-currency-per-group a mismatch is a programmer bug, not user input.
- `parseAmount` is strict: no sign, no exponent, at most 2 decimals, commas only as valid thousands groups, no leading zeros (`007`, `00`, `0,001` rejected; `0`, `0.05` accepted), and capped at int64 max minor units so every parsed value fits the DB column. It returns a `Result`, never throws.
- `formatAmount`/`formatMoney` avoid `Intl` entirely: grouping is done by hand on the bigint's string form. This keeps output exact for any size (no loss above 2^53) and byte-identical on server and in every browser, so there is no hydration mismatch. Format is `MMK 1,234.50` (code, ASCII space, amount; negatives `MMK -1,234.50`, never `-0.00`).
- Added `zod` 4.6.7 (npm `latest` at the time, pinned exact) for input validation; `parseWith` wraps `safeParse` into a `Result` with a field → message map so server code returns errors instead of throwing.
- `tsconfig.json` `target` raised from `ES2017` to `ES2020` so bigint literals (`100n`) type-check. Next.js compiles with SWC, so this only affects `tsc` type-checking.
- `CURRENCY_EXPONENT` is typed `Record<CurrencyCode, 2>`, not `Record<CurrencyCode, number>`: `parseAmount`/`formatAmount` hard-code 2 decimals, so adding a currency with a different exponent must fail typecheck rather than silently mis-scale amounts.
- `zod` was explicitly approved by the user for PR #8 (feat/shared-lib) as an exception to "no unrequested dependency."
- `parseAmount` rejects input longer than 40 characters (int64 max formatted is 25) before running the regex or `BigInt`, so huge strings cost no conversion work. `parseWith` uses `Object.hasOwn` so field names like `constructor`/`toString` are not shadowed by `Object.prototype`.
- OPEN: Sums of many amounts can exceed int64 even though each parsed amount fits; handle in Phase 3 when balances or DB writes exist (e.g. lower per-amount cap or check the sum).
- `parseAmount`'s "At most 2 decimal places" message only fires when the integer part is valid: `TOO_MANY_DECIMALS_PATTERN` reuses `AMOUNT_PATTERN`'s integer-part regex source, so malformed input like `1,23.456` gets the generic "Enter a valid amount" message instead of a misleading decimals hint.
- Design palette: calm, warm-neutral base (paper `#faf8f4`, ink `#23201c`) with a slate-teal primary (`#2f5d62`) — deliberately not the usual blue/green/purple app look. Money states use earthy hues: `owe` clay, `owed` sage. `danger` is a deep wine (`#9b2335`), darker and cooler than clay, so "you owe money" never reads as "error/destructive"; both are always paired with text, never color alone.
- `owe` and `owed` were darkened slightly from the starting values (`#b0573f` → `#a44f39`, `#4f7a5e` → `#487057`) because they measured 4.13:1 and 4.23:1 on their own `*-subtle` backgrounds; they now pass 4.5:1 on paper, surface and subtle backgrounds.
- Two border tokens: `border` (`#e4ded4`, 1.34:1) is decorative only (cards, table rows — WCAG 1.4.11 does not require 3:1 there); `border-strong` (`#8c8479`, ≥3.48:1) is for inputs and other controls whose boundary must be seen.
- Light mode only for now. Tokens use semantic names (`surface`, `ink`, `owe`), not hue names, so a dark theme can later redefine the same tokens without touching components. The create-next-app dark-mode media query was removed.
- Tailwind's default palette is reset with `--color-*: initial` in `@theme`, so classes like `bg-zinc-50` or `text-black` produce nothing. `src/components/noRawColors.test.ts` also fails on raw hex, `bg-[#…]`-style arbitrary colors and default-palette class names in `src/components` and `src/app` (except `globals.css`), so mistakes fail CI instead of silently rendering unstyled.
- Modal uses the native `<dialog>` element with `showModal()` — the browser provides focus trapping, Esc to close, top-layer stacking and `::backdrop`, with no new dependency. The open/close effect checks `dialog.open` first so React Strict Mode's double effect run does not throw `InvalidStateError`.
- `/dev/components` is a dev-only component preview: the page calls `notFound()` when `process.env.NODE_ENV === "production"` (inlined at build), so a production build prerenders it as a 404. It is not linked from anywhere.
- Removed create-next-app's unused SVGs from `public/` and added `public/.gitkeep` — the Dockerfile `runner` stage copies `/app/public`, which fails if the folder does not exist in the build context.
- Class names are joined with a tiny `cx` helper (`src/lib/cx.ts`) instead of adding `clsx` / `tailwind-merge`.
- Observed, cause unconfirmed: after editing `src/app/globals.css`, `next dev` and `next build` kept serving the old stylesheet until `.next/cache/turbopack` (dev: `.next/dev/cache/turbopack`) was moved aside and the app rebuilt. CI and Docker builds start with no cache, so they were not affected.
- DB naming (Prisma defaults): models PascalCase singular (`Group`), fields camelCase (`createdAt`), no `@map`/`@@map`, so table and column names equal the Prisma names. `Group` is an SQL reserved word: any hand-written raw SQL must quote it (`"Group"`). Revisit only if raw SQL becomes common. Ids are `String @id @default(cuid())`; timestamps `createdAt DateTime @default(now())` (Prisma fills it client-side, millisecond precision).
- `Group.currency` is a plain `String` holding `MMK` / `USD` / `KHR`, validated in code with `currencyCodeSchema` (`src/lib/validation.ts`), not by a DB enum/check — SQLite has no enums and the list lives in one place (`src/lib/currency.ts`).
- Any money column will be Prisma `BigInt` (int64 minor units), never `Int` or `Float` — see the Money entry above.
- Server-only code lives in `src/server/` (`db.ts`), not `src/lib/`, so `src/lib` stays framework- and Prisma-free. `getDb()` is a lazy singleton cached on `globalThis` (one client per process, also across dev hot reloads); it throws a clear error if `DATABASE_URL` is missing. Lazy creation means `next build` imports route modules without needing a database. `createDbClient(url)` is exported separately so tests build their own client and never call `getDb()`.
- `/api/health` calls `await connection()` before `SELECT 1`: with Cache Components a GET route handler can be prerendered at build time, and a synchronous better-sqlite3 query might not stop prerendering — the build output now lists it as `ƒ (Dynamic)`. Returns 200 `{status:"ok"}` / 503 `{status:"error"}`, `Cache-Control: no-store`.
- No `serverExternalPackages` added: `better-sqlite3` and `@prisma/client` are on Next.js's built-in auto-external list. Proven by the runner image: the standalone output links `.next/node_modules/better-sqlite3-<hash>` to the adapter's copy and `/api/health` returns 200.
- OPEN: `@prisma/adapter-better-sqlite3@7.10.1` depends on `better-sqlite3@^12.6.0`, so npm installs a nested 12.11.1 that the app actually uses at runtime; the top-level `better-sqlite3@13.2.0` in package.json is only used by the test helper. Two native builds, and tests run on a different driver version than the app. Decide in a separate PR (e.g. pin top-level to 12.x).
- Docker dev uses `./data/docker.db` (`DATABASE_URL=file:/app/data/docker.db`), local dev uses `./data/dev.db`, the runner uses `/app/data/app.db` on a volume. Separated by design rather than by a warning: two processes on one SQLite file across a Docker Desktop bind mount risk lock errors ("database is locked") and corruption, because file locking over the VM file share is not reliable.
- Docker dev starts with `db:generate && db:deploy && npm run dev`: the `.:/app` bind mount hides the image's `src/generated`, so the client is generated at container start; `migrate deploy` (not `migrate dev`) because it never prompts or creates migrations.
- Migrate at container start is chosen because we run one container with one SQLite file; if we ever move to Postgres or several instances, switch to a separate migrate step to avoid racing migrations.
- Runner gets the Prisma CLI from a separate `prisma-cli` stage that installs only `prisma` + `dotenv` at the versions in package.json (`--legacy-peer-deps` so prisma's better-sqlite3/typescript peers are not pulled in), copied into `/app/node_modules` before the standalone output so standalone's traced files win on overlap. Tradeoff: runner image grew (742 MB on disk / 163 MB content) in exchange for zero manual migrate steps.
- `docker-entrypoint.sh`: `set -e`, `migrate deploy`, on failure prints `[entrypoint] prisma migrate deploy failed — not starting the server` and exits 1; then `exec node server.js` so node is PID 1 and gets SIGTERM directly (`docker stop` returns in ~0.1 s). `.gitattributes` forces LF for `*.sh` so a Windows checkout cannot break the shebang with CRLF.
- Runner runs as uid 1001 (`nextjs`); the image creates `/app/data` owned by `nextjs:nodejs` because SQLite needs a writable directory (journal file), not just a writable file. A fresh named volume inherits that ownership. Docker Desktop (macOS) maps bind-mount ownership automatically; on a Linux host the folder must be writable by uid 1001 (`chown 1001:1001`).
- Observed, not fixed: in the runner, Prisma CLI prints "failed to detect the libssl/openssl version" warnings (`node:24-slim` has no openssl), but `migrate deploy` succeeds for SQLite. If it ever fails with a libssl error, install the `openssl` apt package in the runner stage.
- `data/.gitkeep` is committed (`.gitignore`: `data/*` + `!data/.gitkeep`) so a fresh clone has the `data/` folder for local dev.
- Tests: `createTestDb()` (`src/server/testDb.ts`) creates a temp SQLite file under `os.tmpdir()`, runs each `prisma/migrations/*/migration.sql` in sorted order with better-sqlite3, and deletes the single file after each test (`unlinkSync`). This does not write Prisma's `_prisma_migrations` table — fine for throwaway DBs, and it needs no CLI or child process. Tests never touch `DATABASE_URL` or `data/`.
- `db:reset` (`prisma migrate reset --force`) is DEV ONLY: it deletes all data without asking. The agent never runs it, it is not in `.claude/settings.json` allow rules, and Prisma's AI-agent consent guard must not be bypassed with an environment variable — the user runs it.
- CI unchanged: it already runs `prisma generate`; tests use temp DBs and `next build` never opens the database, so no migrate step is needed.
