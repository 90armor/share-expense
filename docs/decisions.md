- Money is stored and computed as integer minor units (1/100) in a `bigint`, typed `Money = Readonly<{ amount: bigint; currency: CurrencyCode }>` (`src/lib/money.ts`). Not float: binary floating point cannot represent 0.10 exactly and drifts on sums. Not Prisma `Int`: it is 32-bit (max 2,147,483,647 minor units ≈ 21.4M MMK), too small for MMK/KHR group totals — the DB column will be Prisma `BigInt` (int64). Not Prisma `Decimal`: SQLite has no true decimal type. Across JSON/forms, amounts travel as strings (bigint is not JSON-serializable).
- Supported currencies are MMK, USD and KHR, all with 2 decimal places. One currency per group; no FX conversion. Arithmetic helpers (`addMoney`, `subtractMoney`, `sumMoney`) throw on a currency mismatch rather than returning a Result — under one-currency-per-group a mismatch is a programmer bug, not user input.
- `parseAmount` is strict: no sign, no exponent, at most 2 decimals, commas only as valid thousands groups, no leading zeros (`007`, `00`, `0,001` rejected; `0`, `0.05` accepted), and capped at int64 max minor units so every parsed value fits the DB column. It returns a `Result`, never throws.
- `formatAmount`/`formatMoney` avoid `Intl` entirely: grouping is done by hand on the bigint's string form. This keeps output exact for any size (no loss above 2^53) and byte-identical on server and in every browser, so there is no hydration mismatch. Format is `MMK 1,234.50` (code, ASCII space, amount; negatives `MMK -1,234.50`, never `-0.00`).

- Equal split rounding (feat/split): `splitEqually(total, participantIds)` in `src/lib/split.ts`. With `total = q × n + r` (bigint division), everyone gets `q` and the first `r` participants in ascending participant-id order get one extra minor unit. So the shares always sum exactly to the total and differ by at most 1 minor unit. The ids are sorted inside the function (on a copy) with plain code-unit comparison (`<`, not `localeCompare`), so the caller's input order never matters and the result never depends on the server or browser locale. The result is returned in that sorted order. Known effect: for the same set of participants, the same member (the lowest id) gets the extra unit on every expense. Accepted because the difference is at most 1 minor unit (1/100 of a currency unit) per expense. Invalid input (empty list, duplicate id, negative total) throws an `Error` instead of returning a `Result`. This follows `addMoney`/`sumMoney` (throw on a programmer bug), not `parseAmount` (`Result` for user input): callers pass already-validated expenses (amount > 0, 1–100 unique participants), so bad input means a bug or corrupt data, and a `Result` would make every balance caller unwrap an error that cannot happen. - Balance logic (feat/balance-logic): pure functions in `src/lib/balance.ts`, no DB, service or UI yet. `computeNetBalances(expenses)` takes plain data (`{ payerId, amount: Money, participantIds }`). For each expense the payer is credited the full amount and every participant is debited their share from `splitEqually` (reused, not re-implemented); net = credited − debited. Because the shares of one expense sum exactly to its amount, the nets of a group always sum to 0. The result has one entry per id that appears in an expense (payer or participant), including nets of 0, sorted by id in code-unit order, so the input order never matters. Members with no expenses are the caller's job: the function never sees the member list, and the caller already has it and shows them as 0.
- Transfers (feat/balance-logic): `computeTransfers(nets)` uses a deterministic greedy. Each step takes the debtor who owes the most and the creditor who is owed the most, and the debtor pays the smaller of the two amounts. After every transfer both the debtor and the creditor lists are re-evaluated: the leftover of the member who was not zeroed goes back into the comparison with everyone else. Ties are broken by member id ascending (code-unit order, like `<`, no locale), so the same nets always give the same transfers in the same order on any server or browser, whatever the input order. Members with net 0 appear in no transfer. Each transfer zeroes at least one member and the last one zeroes two, so there are at most (members with a non-zero net) − 1 transfers. The output is in the order the greedy produces it. Why greedy: finding the exact minimum number of transfers is NP-hard, and the greedy is simple, exact in bigint and bounded. Why biggest-first: the largest debts are settled in as few transfers as possible.

- Expenses table, long names (PR "keep Amount visible"): a 100-character name or description with no spaces widened the table past its wrapper, hiding Amount. Measured in a browser at 1280px and 375px (wrapper 620px / 291px) against a normal group, 30-40 character descriptions and 100-character names. What did **not** work: (1) `break-words` (`overflow-wrap: break-word`) does not lower a table column's min-content width, so the column stays 100 characters wide. (2) A `max-w` cap on the cell content clamps max-content too: `max-w-28` made "Breakfast (Banh mi)" and "Callisium, Gregory, Holland" wrap at 1280px with plenty of spare width; larger caps (10rem, 12rem, 30ch) either still changed normal data or still scrolled with long names; one cap cannot satisfy both. (3) `wrap-anywhere` on the cells lowers min-content, but it made the Paid by column 1px narrower in the mid-length-description group and broke "Gregory" mid-word, so normal data differed from main. (4) Ellipsis has the same width constraint as a cap. (5) `sticky right-0` on Amount in the third column did not work: sticky only pushes a cell left, so Amount scrolled away once you passed it (hidden at the far right). **Chosen:** Amount is the last column and `sticky` (`sticky right-0`, opaque `bg-paper` header / `bg-surface` cells, a left separator drawn with an inset shadow from the `border` token because collapsed borders do not travel with a sticky cell). Normal data at 1280px is unchanged (same line counts, no scroll, same widths with the last two columns swapped); with 100-character names Amount stays at the right edge at every scroll position. Long text is **not** wrapped: the table scrolls sideways and the long text is read by scrolling. While scrolled, the pinned Amount covers the text under it. Node tests only check classes, not layout.
- Phone layout is **not** fixed: with four columns the Expenses table already scrolls sideways at 375px on main even for normal names (445px of content in a 291px wrapper), so Amount was hidden on phones whatever the name length. Amount is now pinned there too, but it covers part of the neighbouring text until you scroll (at scroll 0 it overlays part of "Paid by" with normal names). A real small-screen layout (for example stacked rows) is a separate decision.
- Name limits (fix/lower-name-limits): member name ≤ 40 (`MEMBER_NAME_MAX_LENGTH`), group name ≤ 60 (`GROUP_NAME_MAX_LENGTH`); description stays ≤ 100. Why: real names are short, and 100-character names cost a lot of time on layout edge cases. `NAME_MAX_LENGTH` is gone; `nameSchema` is now `nameSchema(maxLength)`. Message: "Name must be at most N characters"; hint: "Up to N characters".
- Names count **visible characters (graphemes)**, via `Intl.Segmenter(undefined, { granularity: "grapheme" })`, not UTF-16 code units. Why: Burmese uses about 2 code units per visible character ("ကို" is 3 units, 1 grapheme; "ဒေါ်ခင်မြင့်ကြည်" is 16 units, 8 graphemes), so a 40-unit limit would reject a Burmese name of about 25 visible characters. Backstop: at most `maxLength × NAME_MAX_CODE_UNITS_PER_CHAR` (4) code units, because one grapheme can be any length ("a" + 200 combining marks is 1 grapheme). The backstop runs first with zod's `abort: true`, so a huge string is never segmented. Real Burmese names average about 2 units per grapheme, far under 4. The count runs after `.trim()`, on the name as typed (NFC is only for `nameKey`). Grapheme rules come from the runtime's ICU, so a rare string could count differently on another Node/ICU version.
- Supersedes the name part of the `maxLength` note above: the group and member name inputs no longer set `maxLength`, because HTML `maxlength` counts code units and would stop a Burmese name after about 20 visible characters. The hint stays, and the server message shows the limit. The description input keeps `maxLength={DESCRIPTION_MAX_LENGTH}` and still counts code units (unchanged in this PR).
- Existing rows over the new limits are not changed (no migration, no data fix). Reads do not re-validate names, so they still display, with the existing protections (`min-w-0`, `break-words`, sticky Amount). The MVP cannot edit names; payer, participants, settlements and member removal use ids only, so a legacy long name keeps working everywhere. Layout tests keep 100-character names on purpose, to cover these rows.
